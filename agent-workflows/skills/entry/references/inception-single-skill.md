# Inception: one Skill per conversation

This operating rule applies to Group B (purpose), Group C (outcomes and
measurement), and Group D (planning). It supersedes the original group-only
clear convention for these groups. Group A and Group E onward keep their
existing orchestration. Apply this rule even when an orchestrator invokes the
Skill or there is ample context remaining.

## Start and scope

### Pre-Run helper (new intake and rehearsal)

Use the installed absolute
`/absolute/project/.agent-workflow/bin/agent-workflow-inception init/save/resume`
entrypoint for deterministic project-local persistence.
When Skills are installed project-locally under `.agents/skills`, install the
matching runtime snapshot with
`python3 /absolute/source/agent-workflows/scripts/install-project-local-inception.py
--project /absolute/project`. Then use only the emitted
`/absolute/project/.agent-workflow/bin/agent-workflow-inception` wrapper. The
create-only installer refuses conflicting project files; it copies the same
snapshot's Skills, runtime and schemas and binds their byte digests in
`.agent-workflow/SNAPSHOT-MANIFEST.json`. The wrapper checks every bound file
before each command, so it does not guess PATH or a project-relative
`PYTHONPATH`. A source checkout may still use
`PYTHONPATH=/absolute/source/agent-workflows/src python3 -m
ai_agent_workflow.inception_cli`; do not use the relative form in another
project.
This helper does not replace the Group B/C/D compilers, Group closure, or Run
adoption. Its `recorded` status means a saved **draft**, never Skill acceptance;
`compiler_status: not-run` and `group_acceptance: not-performed` are explicit.

1. Save the user's verbatim request into a file. Confirm `.local/` is ignored.
   Run `/absolute/project/.agent-workflow/bin/agent-workflow-inception init
   --project /absolute/project --work-id task-id --request /absolute/request.txt`.
   It saves intake/request with `workflow-loop/v1` progress control, not a Run
   or HEAD. Existing IDs refuse rather than overwrite a request or reset loop history.
2. For entry, write JSON with exactly `raw_request_ref` (copied from intake),
   `interpretation` (string), `assumptions` (array), and `unknowns` (array).
   Other draft outputs keep the selected Skill's substantive requirements.
3. Run `/absolute/project/.agent-workflow/bin/agent-workflow-inception save
   --intake /absolute/intake.json --skill entry --output /absolute/output.json
   --status recorded --started-at <timezone-aware-step-start>`. Subsequent calls
   also pass `--previous /absolute/handoff-NNNN.json`, plus any `--input` refs,
   `--check` results, and `--unresolved` items. A blocked/question step uses
   `blocked`/`needs-input` and remains the next selected Skill.
4. `save` is the only writer of `handoff-NNNN.json`; never handwrite, copy, or
   edit one. It adds a helper proof and internally verifies persistence. If the
   helper is unavailable or `save` fails, report `blocked` and retain the
   conversation; an agent-authored JSON file or success message is not a
   frontier. Candidate output must not reuse the reserved handoff fields
   `compiler_status`, `group_acceptance`, or `execution_authorized` for selector
   results; those names only express the helper's non-authoritative invariants.
5. After clear, run `/absolute/project/.agent-workflow/bin/agent-workflow-inception
   resume --handoff /absolute/handoff-NNNN.json` before reading the handoff as state. Continue
   only when it returns `frontier_status: helper-verified`; it verifies the
   helper proof and every bound digest and reports the immutable frontier and
   loop-control mode. It executes no Skill. Store outputs as new immutable versions,
   since changing a referenced file invalidates resume.

Normal pre-Run drafts may be prepared through B7. Draft recording alone does
not perform Kernel approval or Group closure: `save/resume` stops at B7 without
suggesting C1. Use the explicit runtime adoption below to validate the physical
receipt and commit approval. Changing `mode` does not approve a draft.

Only an explicitly requested isolated test may use `init --mode rehearsal`.
It supports draft handoff rehearsal through all 25 B/C/D Skills, separate from
normal accepted execution. Mock dialogue/approval receipts must contain
`source: mock`, `work_id`, and `subject` (exact output path/version/digest).
An objective receipt also requires `decision: approve`, `explicit: true`,
`actor`, and timezone-aware `recorded_at`; pass it with `save --receipt`.
Real mode requires `source: human`, supplied from actual human evidence, not
generated by the AI. Both are recorded local receipts, not authenticated
Kernel authority. Rehearsal mode persists across every handoff and
`resume --require-real` rejects it. Draft rehearsal output alone never
authorizes Group E or claims B/C/D acceptance. At D12 the draft helper stops.
An explicitly authorized sandbox test may separately use the runtime path;
its mock provenance remains isolated from real approval and live operation.

These draft/rehearsal rules do not weaken the accepted-Run protocol below.

### Project-local runtime (physical approval and actual compiler results)

The installed absolute
`/absolute/project/.agent-workflow/bin/agent-workflow-inception runtime`
entrypoint connects prepared inputs to the actual
ObjectiveSystemV1, OutcomeSystemV1, PlanningSystemV1 and ControlKernel. From
an explicitly labelled source checkout use
`PYTHONPATH=/absolute/source/agent-workflows/src python3 -m
ai_agent_workflow.inception_cli runtime`; that source-only form is not a
project-local operational command. This is a deterministic adapter,
not a model runner: the caller still invokes one Skill, saves its output,
stops, clears context, and explicitly invokes the next Skill.

For the runtime adapter's `adopt` operation, prepare a JSON object with `intake_ref`, `candidate_ref`,
`proposal_ref`, `actor_ref`, `receipt_ref`, and `mode` (`real` or `rehearsal`).
New Run adoption binds `workflow-loop/v1`; `legacy_budget_seconds` is accepted
only for an explicit old-format adoption. Each ref has an absolute project-local `path`,
`version`, and SHA-256 `digest` of the physical bytes. Candidate and intake
versions must differ. The actor document identifies `actor_id` and `source`
(`human` for real, `mock` for rehearsal).

Use `runtime_approval.approval_context(...)` to obtain the exact receipt
binding fields for those inputs. It only returns context; it creates no
approval. Persist the actual supplied decision with `receipt_id`, `issued_at`
(timezone-aware), `decision: approve`, and `explicit: true`. Do not generate a
human response. Adoption validates the receipt, invokes B7 and commits the
Kernel objective-approval transaction; immutable loop history and phase
counters are retained across restarts and context changes.

The required `preapproval_steps` is a JSON array of six
`[qualified_id, inputs]` pairs, exactly B1 through B6 in order. Supply the
saved substantive inputs from the earlier individual Skill invocations.
Adoption recompiles and publishes those results; it does not launch six AI
Skills or attest that clear happened. Missing, incomplete, or out-of-order
B1–B6 inputs are refused before any Run is registered; B closure requires every B result.

The following paths and IDs are user-entered examples. Replace them with
existing project files and the actual Run ID; these commands show no claimed
successful run.

```sh
/absolute/project/.agent-workflow/bin/agent-workflow-inception runtime adopt --project /absolute/project \
  --run-id work-id --inputs /absolute/project/adoption-args.json
/absolute/project/.agent-workflow/bin/agent-workflow-inception runtime status --project /absolute/project --run-id work-id
```

After successful B closure and explicit advance to C, a fresh caller reads
`status` and invokes only its `next_id`. `step` accepts current C/D inputs and
the same physical actor file used for approval:

```sh
/absolute/project/.agent-workflow/bin/agent-workflow-inception runtime step --project /absolute/project --run-id work-id \
  --qualified-id group.C.C1 --inputs /absolute/project/c1-inputs.json \
  --actor /absolute/project/actor.json
```

The adapter validates physical inputs, current objective, predecessor and
compiler output, then publishes the actual result in the Kernel. C6 binds
the exact current C1–C5 outputs. D inputs include the current predecessor's
physical Kernel object; D12 evidence includes D1–D11. D6 also requires a
physical option-selection receipt for the approved actor, objective digest
and current D5 object digest. A mock option response is accepted only within
rehearsal provenance. A refusal or stale input does not complete a step.

At the real Group boundary, save an audit JSON with `group_id`, current
`objective_digest`, `alignment: aligned`, `reviewer`, `rationale`, and
`artifact_refs` containing that Group's exact current Skill object refs in
route order. The audit must describe the review actually performed. Invoke:

```sh
/absolute/project/.agent-workflow/bin/agent-workflow-inception runtime close --project /absolute/project --run-id work-id \
  --inputs /absolute/project/group-audit.json
```

`close` runs F1–F7 and commits the actual Epoch/Group closure. It returns
closure evidence references. Inspect failures: closure spans multiple Kernel
transactions, so a crash can leave partial closure. Inspect the canonical
HEAD and receipts. If F6 was accepted, repeating `close` with the identical
audit and evidence resumes only F7; if F7 was accepted it returns the same
report without advancing HEAD. Changed evidence is refused. Interruptions
inside F1–F5 remain fail-closed and require inspection; do not skip gates or
assume retry will complete those earlier phases.

After completed closure, stop and clear. In the fresh conversation, invoke
`"$PROJECT_ROOT/.agent-workflow/bin/agent-workflow-inception" runtime status`
in a new process, read the physical outputs and receipts,
then explicitly advance when authorized:

```sh
/absolute/project/.agent-workflow/bin/agent-workflow-inception runtime advance --project /absolute/project --run-id work-id
```

`advance` opens the next Group only after closure; it does not close one
implicitly. Status and new-process resume read the persisted Kernel, without
requiring conversation history. Neither command clears host context itself.
After D closure, E uses the existing Kernel execution APIs under the supplied
authority. This adapter neither launches models nor establishes a completed
production benchmark. An isolated runtime exercise is not evidence of live
activation, Nix rebuild, Git publication, or production effectiveness.

Run only the explicitly selected Skill. Read its physical inputs and the
supplied handoff; do not reconstruct missing decisions from conversation
history. If the user supplies a new request without a handoff, `entry` can
start by saving that request. Other Skills require their stated inputs.

Use the selected Workflow's order. Profile operations hosted by the current
Skill belong to its work, not to a second automatic Skill invocation. A helper
may perform a bounded investigation within this Skill when otherwise allowed;
do not delegate subsequent Skills or the remaining Inception phase.

For the complete path the named Skills are:

- B: `entry` → `discover-context` → `classify-scope` → `grill-purpose` →
  `propose-true-purpose` → `assess-feasibility-and-constraints` → `approve-objective`.
- C: `decompose-outcomes` → `build-outcome-dependency-graph` → `design-measurement` →
  `define-targets` → `capture-baseline` → `validate-outcome-system`.
- D: `select-workflow-profile` → `reverse-engineer-current-system` →
  `discover-practices` → `specify-what-and-why` → `explore-options` →
  `design-solution` → `design-contracts` → `decompose-tasks` →
  `sequence-and-parallelize` → `prepare-worker-briefs` →
  `plan-verification-and-recovery` → `implementation-readiness-review`.

## Finish and persist

Save the Skill's actual output, then have the helper create and resume-check
the compact handoff before recommending clear. Do not create a handoff with a
text editor, shell redirection, or a generic JSON writer. Use the project's
existing authorized work directory; for a new
intake use an ignored `.local/agent/inception/<work-id>/` directory. Confirm
that it is ignored before storing private request material. This handoff is
not a new Run, objective approval, kernel checkpoint, or current pointer.

Keep handoffs as separate versioned files, for example
`handoffs/003-classify-scope.md`; never overwrite an earlier handoff. Include:

- Work ID, selected Workflow/profile and version, current Skill, and status:
  completed, needs-input, or blocked.
- Raw request reference, purpose/objective reference, scope and continuing
  user constraints. Use null for an objective that does not exist yet.
- Output and next-input references, each with absolute path, version, and
  SHA-256 of the physical bytes; include the applicable authority/approval
  receipts without treating a candidate as approved.
- Checks actually run and results, unresolved questions, required corrections,
  accepted decisions, loop identity/history, phase counters, and any recovery
  requirement. Clearing context never resets a counter or discards an accepted decision.
- Exactly one next Skill, its start conditions, and a copyable invocation
  naming this handoff's absolute path. Record any group-closure work still
  pending. Include only inputs needed by the next Skill, not the entire chat.

Accept the saved handoff as a frontier only from helper `resume` output with
`frontier_status: helper-verified`. If persistence or verification fails,
report the error and keep the conversation available; do not recommend clear
or claim that the step has completed.

## Stop, clear, and resume

After saving, show the outcome, output links, and the exact next invocation,
then end the turn. Do not call the next Skill, launch it as a subagent, or
continue a parent orchestration loop in the same conversation. A normal
handoff is advice; it is not evidence that clear happened.

The human clears context using the host's supported operation, or starts a
fresh conversation without copied history, and pastes the next invocation.
Example: `Use $discover-context. Read /absolute/project/.local/agent/inception/work-id/handoffs/001-entry.md and execute only discover-context.` The agent
does not claim to have cleared the host itself. Resuming a needs-input or
blocked step invokes that same Skill; an explicit correction routes to the
owning upstream Skill. Neither advances the normal frontier as completed.

On resume, first run
`/absolute/project/.agent-workflow/bin/agent-workflow-inception resume --handoff
/absolute/project/.local/agent/inception/work-id/handoff-NNNN.json`; never trust
the handoff path or an agent's previous final message by itself. Only after a
`helper-verified` result, read its physical inputs and verify the bytes against
their recorded digests before doing work. Missing or stale inputs require a
new helper-generated handoff. Read the referenced raw request and relevant constraints even when
the new conversation has no history. Reuse valid recorded approvals within
their original scope; clear does not require a human to approve them again.

A conversational question within a Skill may be answered before its output
is ready. Do not force clear between that question and the answer. Clear is
the boundary between completed Skill invocations, or an explicitly saved
interruption, rather than between every message/tool call.

## Group closure and Construction

Keep existing Group closure requirements. At the actual B/C/D boundary,
finalize the required bundle/checkpoint once under the existing owner and
authority; these shared protocol operations do not start another business
Skill. A Skill boundary inside a group must not mark the group closed or run
the full F1–F7 group closure each time. If closure cannot complete, record it
as pending and do not advise advancing into the next group.

After `implementation-readiness-review`, preserve its readiness disposition,
accepted risks, approvals, and the completed D closure. After clear, the
human explicitly invokes `execution-preflight` with that handoff. Group E
then uses its existing parallel execution, two-stage review, and finite
feedback loops. A not-ready result returns to its named upstream owner.
