AI Agent Workflow / User Guide

会話で入り、
境界だけ握る。

まず「何を達成したいか」「どこまで任せるか」を伝える。目的・成果・計画を固めるInceptionでは、Skillを1つ実行して成果を保存し、clear後に提示された次の呼び出し文で進む。実装段階ではWorkflowが作業をオーケストレーションする。

最重要： Go や 続けて は、すでに承認した範囲内を継続する指示。Git操作、実generationのactivation、外部操作、秘密の取扱いなど、別に区切られた権限まで自動で広げない。
自然文が標準入口 状態は物理ファイルから復旧 高リスク操作は別承認

Quick start

最短の使い方

最初から完璧な仕様を書く必要はない。次の4点があれば、Workflow側が不足を調べ、結果を変える質問だけを返す。

1

対象

何についての仕事か。repository、機能、文書、業務processなど。

2

期待する変化

何がどうなれば成功か。原因が分かる、実装が通る、移行できる、など。

3

今回の境界

調査だけ、実装まで、Rebuild手前、commitなし、など。

4

制約

期限、触らない場所、既存diff、利用者確認が必要な判断。

この不具合の根本原因を調べて。対象はagent-workflows、既存の利用者変更は保持。まず診断だけで、修正はまだしない。
Inceptionは1 Skillずつ： 最初は $entry に依頼を渡す。以後は各Skillが返す成果物・handoffリンクと次の呼び出し文を確認し、clearまたは履歴なしの新規会話を行ってから、その文を貼り付ける。Skill名を暗記する必要はない。
$entry を使って、この依頼を保存して整理して。今回はentryだけを実行し、成果物とhandoff、clear後の次のSkill呼び出し文を返して。

対象は目的探索・承認（B）、成果と測定（C）、実装計画（D）の25 Skill。途中の質問は同じSkillで続け、承認待ちや要修正を完了扱いしない。実装準備確認とDのまとめが通ったら、clear後に execution-preflight を明示起動して実装へ進む。運用変更の詳細

Task map

どんなタスクで入るか

カードを絞り込むと、依頼の型とWorkflow側の扱いが分かる。

ONE-OFF

質問・説明・小さな確認

読み取り中心で、短く、状態を残さなくても再現できる仕事。

この関数が何を保証しているか説明して。変更はしない。
MANAGED

調査・設計・レビュー

複数source、判断、独立レビュー、引継ぎがある仕事。成果と停止理由をRunへ残す。

目的と上流の決め事だけを与えて、全体を独立レビューして。修正はしない。
MANAGED

機能追加・bug fix・改善

現状、仕様、実装、検証をつなぐ仕事。必要なら分割し、成功済みの枝を保持する。

再現→根本原因→回帰test→最小修正→全体検証まで進めて。Git操作はしない。
SEPARATE GATE

移行・activation・外部操作

戻し方とdry-runを先に作り、実切替、Git、外部system変更は個別の権限として扱う。

dry-runとrollback確認まで。実generationのswitch、commit、pushはしない。
Entry

エントリー時に起きること

最初の依頼は「暫定目的」。いきなり実装へ飛ばず、現地で分かることを調べ、結果が変わる点だけ確認してから目的と権限を固定する。

INPUT自然文の依頼

原文と解釈を分ける。

LOOKUP既存Run確認

重複ならresumeか新規かを判断。

ROUTEone-off / managed

規模、risk、可逆性で深度を選ぶ。

DISCOVER先に現地調査

回答可能な質問を利用者へ戻さない。

CONFIRM目的と境界

非目的、制約、停止点を揃える。

APPROVE目的version

明示承認後だけ保護された正本になる。

小さい仕事： 説明、読み取り、軽微で可逆な変更は、重いRunを作らないone-offにできる。
管理する仕事： 複数phase、worker、承認、長時間、依存、監査、復旧があるならmanaged Runにする。
Steering

途中でどう指示するか

指示は「目的を変える」のか、「同じ目的の範囲内で進め方を変える」のかを区別する。曖昧な短語は既存権限を拡張しない。

新しい仕事を始める

対象、期待する変化、今回の境界、制約を自然文で伝える。目的は暫定として記録され、必要な確認後に承認する。

この不具合を調査して。期待値はX、実際はY。まず原因特定まで、修正はしない。
着手

「この不具合を原因調査して。修正はまだしない」— 読取・診断を許可し、source変更は許可しない。

目的承認

「この目的v1、非目的、制約で進めて」— 目的を正本として固定する。後から変えるなら影響分析と新versionが必要。

実装範囲

「把握済みのrequired findingを修正し、A6R完了まで承認なしで進めて」— その範囲の実装を委任するが、別gateは残る。

継続

「Go」「続けて」— 既存目的・scope・権限内の次の安全な一手へ進む。新しい権限は生まれない。

停止点

「Rebuildの手前まで」— build、dry-run、rollback確認までは進めても、実switchは行わない。

観測

「現在地と停止理由を返して」— 目的、完了、現在Group/Epoch、未検証、次の一手を物理stateから読む。

Prompt recipes

そのまま使える指示レシピ

内部commandを覚える代わりに、期待結果と権限境界を一文で固定する。

DIAGNOSE ONLY

原因だけ調べる

診断は修正権限を含まない。

症状、期待値、実値、環境を確認し、再現と根本原因まで診断して。修正はしない。原因、証拠、未検証riskを返して。
RESEARCH

調査だけ委任する

結論だけでなく、sourceと不確実性を残す。

この選択肢を一次資料とcodebaseから調査して。現状維持を含む案、推奨、反証条件をまとめて。実装はしない。
DESIGN GATE

設計後に止める

設計承認と実装承認を分ける。

As-Is、To-Be、non-goals、選択肢、推奨設計、migrationとrollbackまで作って。実装readiness review後に止まり、sourceは変更しない。
AUTONOMOUS BOUNDARY

境界まで自律実装

通常の実装判断は委任し、止める操作を列挙する。

承認済み目的とplanの範囲で、required findingの修正、test、独立reviewまで承認なしで進めて。目的・scope変更、実activation、Git、外部操作が必要なら止めて。
FINITE REVIEW

二段階レビューを有限化

候補抽出と必要性判定を分ける。

ReviewerはBackground、As-Is、canonical To-Be、Gap、証拠付きcandidateを出して。別Validatorがrequired / defer / reject / needs-userを判定し、requiredだけ修正。重複、理由ある選択、軽微、好みはloopへ戻さない。時間・round・attempt上限で停止理由を残して。
RESUME

長期作業を再開

会話の記憶ではなく、最新HEADとCheckpointを読む。

A6Rを再開。最新の物理stateを検証し、目的、完了済み、現在地、停止理由、未検証、次の一手、残る権限gateを返してから進めて。
INDEPENDENT REVIEW

前提を絞った全体レビュー

実装経緯を与えず、正本と成果だけで評価する。

目的と承認済みの上流決定だけを入力に、成果物全体をfresh contextでレビューして。変更候補をBackground、As-Is、To-Be、Gap、証拠付きで返し、修正はしない。
PREACTIVATION

切替直前まで進める

戻せる証拠を作って、最後のswitchを残す。

Rebuildの手前まで進めて。source test、Nix build、downstream dry-run、rollback確認、実行予定commandの提示まで。実generation activation、stage、commit、pushはしない。
Lifecycle

想定される全体フロー

必要なGroupだけを使う。小さい仕事を全工程へ通すのではなく、riskと成果に応じて深度を変える。

GROUP B目的理解と承認

暫定目的を調べ、真の目的と非目的を承認。

GROUP C小目的と計測

達成状態、指標、baseline、targetを接続。

GROUP D仕様・設計・計画

As-Is、spec、選択肢、設計、task、検証計画。

GROUP E実行と収束

Worker、二段階review、required-only fix、全体検証。

GROUP G判断の永続化

候補を重複整理し、利用者承認後だけADR等へ昇格。

GROUP H目的監査と完了

作業量ではなく目的を達成したかを最終判定。

保存とclear： Inceptionでは毎Skillの成果物とhandoffを保存してclearする。Group全体の成果、検証、決定、未解決、無効化、次入力のまとめ（共通closure）はGroup終了時に一度行う。Skill途中のclearでGroupを完了扱いしない。
Two-stage review

レビューと「直すべきか」を分ける

Reviewerが見つけたものを即修正しない。別のfresh Validatorが、現在の仕事に本当に必要かを判定してからfix authorityを出す。

PHASE 1

Candidate review

Background、As-Is、canonical To-Be、Gap、requirement、証拠、fingerprintを持つ候補を作る。

→
PHASE 2

Finding validation

別actorが正本、承認済みdecision、過去Finding、対象diffと照合し、admissionを決める。

→
BOUNDED LOOP

Requiredだけfix

該当枝だけ修正し、fresh Reviewerが同じFinding IDを再検査する。

required

正しさ、安全性、必須要件、回帰のため今直す。

defer

妥当だが今回の受入条件を変えない。完了をblockしない。

reject

重複、既解決、scope外、根拠のない好み。

needs-user

spec、scope、risk、budgetの選択を変えるため利用者判断。

無限loopを防ぐ： dispatch前にdeadline／timebox、最大review round、Findingごとの最大fix attemptを固定する。枯渇したらworkerを増やさず、成功済み成果、未解決Finding、停止理由をdurable stateへ残す。再開には新しいbudgetの明示承認が必要。
Authority

どの言葉が、どこまで許可するか

実装の承認と、配布・切替・公開の承認は別物。以下は通常の解釈であり、指示内で明示的に広げた範囲が優先される。

利用者の言葉許可すること許可しないことWorkflowの返答
「調査して」「診断して」read-only探索、再現、原因と証拠の特定source修正、設定変更、外部操作原因、証拠、確度、未検証、修正候補
「実装して」「直して」指定scope内のsource変更と相応の検証Git stage/commit/push、deploy、activation変更、test、review、残risk
「完了まで承認なし」すでに承認した目的・scope内の通常判断と反復目的変更、破壊的操作、秘密、live環境、Git、外部systemの別gate境界まで継続し、別権限が必要な地点で停止
「Go」「続けて」現在の承認済み次工程未承認scopeへの拡張、停止条件の解除同じRunを進めるか、明示された停止点で止まる
「Rebuild手前まで」test、build、dry-run、rollback確認、予定command提示実generation switchgeneration rebuild のpreactivation checkpointと正確な未実行command。全面判定とは扱わない。
「commitして」「pushして」指定Git操作のみ。targetと差分を先に検証deployやactivation（別途明示がなければ）commit identity、対象、結果、残る変更
「目的をXへ変える」影響分析、新objective version候補の作成と承認過去の目的・履歴の上書き影響、無効化される成果、再計画、承認点
別承認になりやすいもの： 真の目的・scope・risk・予算・ownerの変更、既存設定の削除／上書き／移行、実activation、Git stage/commit/push、外部system操作、secret取扱い、復旧不能なcleanup。
Continuity

長時間でも、会話に依存しない

会話のsummaryやcompactionは案内であって正本ではない。再開はHEAD、transaction、Artifact Bundle、Checkpointのdigestを検証して行う。

Epoch

意味境界で閉じる

調査→mutation、設計→実装、実装→独立review、authority変更、正本version変更では、tokenに余裕があってもContext Epochを閉じる。

Bundle

次に必要なものを固定

canonical artifactのpath/version/digest、合格証拠、承認済み決定、未解決、無効化、次入力を束ねる。

Resume

停止理由まで復元

目的、完了、現在地、未検証、open finding、budget terminal、次Skillを物理stateだけから返す。

聞き方期待する返答進行するか
「現在地と停止理由」目的version、完了済み成果、現在Group/Epoch、停止理由、未解決、残budget、次の一手読み取りのみ
「A6Rを再開」最新stateの鮮度とdigestを検証し、許可済みscope内で次transitionを実行進行する
「再開前に状況だけ」resume briefは作るがdispatchしない読み取りのみ
「停止してCheckpointを作って」部分成功、失敗、stop reason、次入力を保存し、安全にleaseを閉じる停止する
Context予算： 目安はtarget 200K、通常上限300K、運用上の絶対上限500K。実測できなければ estimated または unavailable とし、推定値を正確な値として扱わない。

Glossary

最小用語集

利用者が操作する必要はないが、statusの読解に役立つ語だけを載せる。

Workflow / Group / Skill
Workflowは目的達成までの全経路。Groupは成果をまとめる工程群。Skillは一つの成果物を作る最小手順。Inception相当のB/C/Dでは1 Skillごとに保存・clear・明示再開し、E以降は既存のオーケストレーションで進める。
Context Epoch
Groupの意味を変えずに、会話文脈を閉じて物理成果へ固定する実行時単位。第四の業務階層ではない。
Artifact Bundle / Checkpoint
成果物参照、digest、証拠、決定、未解決、次入力を束ねた再開の正本。会話summaryより優先される。
Controller / Orchestrator
Controllerは利用者との薄い窓口。Orchestratorだけが検証済みcommandでcanonical HEADを更新する。
Worker / Reviewer / Validator
Workerは成果を作る。Reviewerはcandidateを出す。Validatorは修正必須かを独立評価する。Workerは自分のFindingをcloseできない。
Arbiter
review衝突、budget枯渇、仕様欠陥、分解失敗など通常loopが収束しない例外を整理する役。利用者のprotected approvalを代行しない。
Release scope / Workflow readiness
Release scopeはA6/A6R/A7のような限定された実装単位。局所scopeの判定と全面判定は別に導出する。全面判定の成立には正本の全coverage、必須surface、目的監査が必要。
Generation rebuild / Workflow rebuild
Generation rebuildはNix/Home Managerの切替操作。Workflow rebuildは60 contractと23 profile stepを含む全面計画。単独の「Rebuild直前」は使わず、どちらの境界かを明記する。
