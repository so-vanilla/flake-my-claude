01 / QUICK START

最初にどう指示するか

1. 新しい依頼

$entry と、目的・対象・欲しい成果物・制約を伝える。最初から解決方法を決め切る必要はありません。

2. 1 Skillずつ進める

出力とhandoffを保存できたらclear。返された次のSkill名とhandoffの絶対パスを、新しい会話へ渡します。

3. 実行を委ねる

D12がready、Dの終了処理も完了したらclear。$execution-preflight を明示してEを開始します。

新しい依頼の例

$entry
対象プロジェクト：/absolute/project
目的：問い合わせ対応の見落としを減らしたい。
欲しい成果物：現状整理、改善案、採用案の検証結果。
反復上限：計画段階でphase policy、論理作業ID、検証範囲、回復経路を固定する。process timeoutは進捗制御と分離する。
制約：実顧客情報は使わない。外部送信・本番変更は別承認。
今回はentryだけを実行し、出力と物理handoffを保存してください。
終了時に、保存先・未解決事項・次Skillの呼び出し文を返してください。

上のパスは記入例です。実際の絶対パスに置き換えます。初回には依頼の原文や参考資料も物理ファイルへ保存します。新規か既存Runの再開かが曖昧なら、重複Runを作らず確認します。

clear後の指示の例

$discover-context
/absolute/project/.../handoff-0001.json を読み、参照先と鮮度を確認してください。
discover-contextだけを実行してください。
承認済みの範囲・未解決事項・残予算を引き継ぎ、次Skillは自動実行しないでください。
出力と次のhandoffを保存し、次回の呼び出し文を返してください。

25個のSkill名を覚える運用ではありません。毎回のhandoffから、次に呼ぶ1個を受け取る運用です。「続けて」だけでB/C/Dの残り全部を処理させないでください。

03 / INCEPTION · 25 SKILLS

B/C/D：この順で1つずつ呼ぶ

各行が1回の明示的なSkill呼び出しです。正常終了したら「出力保存 → handoff保存 → clear → 次の行」。質問への回答待ちや上流への差し戻しでは、この直線順から分岐します。名前のリンクは各Skillの実装説明へ移動します。

B — 何のために取り組むか

ID呼ぶSkillやること・受け取るもの
B1$entry依頼原文、解釈、仮定、不明点を分離した受付票。
B2$discover-context既存資料・現状・周辺事情を、出典付きで整理。
B3$classify-scope調査か変更か、対象・所有者・戻せる範囲を分類。
B4$grill-purpose資料から分からない、目的に影響する問いを1つずつ人に聞く。
B5$propose-true-purpose真の目的の候補と推奨を提示。選択は人間が行う。
B6$assess-feasibility-and-constraints時間・権限・環境等の制約から実現可能性を確認。
B7$approve-objective明示された人間の承認を、対象目的と結び付けて記録。AIが承認を代行しない。

新規案件のB1〜B6はpre-Run draftから始まります。B7で実Runへ採用する際は、保存済みB1〜B6の全入力を実compilerで検証・記録します。まとめて6回のAI判断をやり直す意味ではありません。Bのclosure完了後にclearしてCへ進みます。

C — 「できた」をどう判定するか

ID呼ぶSkillやること・受け取るもの
C1$decompose-outcomes承認された目的を、検証できる小目的へ分解。
C2$build-outcome-dependency-graph成果同士の前提関係と担当をグラフ化。
C3$design-measurement測定方法、データ源、頻度、取得可能性を設計。
C4$define-targets期限付きの目標水準を決める。
C5$capture-baseline比較に使う現状値を観測証拠から記録。未取得はゼロにしない。
C6$validate-outcome-system目的→小目的→測定→目標→現状値のつながりを検証。

D — 誰が、何を、どの順に作るか

ID呼ぶSkillやること・受け取るもの
D1$select-workflow-profile案件に合うWorkflowと必要なGroupを選ぶ。
D2$reverse-engineer-current-system現行の構造・流れ・境界を把握。コード以外なら既存業務や文書が対象。
D3$discover-practices実際の開発・レビュー・運用規則を出典付きで整理。
D4$specify-what-and-why何が必要で、なぜ必要かを正本仕様にする。手段を混ぜない。
D5$explore-options現状維持も含む選択肢とトレードオフを比較。
D6$design-solution承認された選択肢を実装可能な設計へ。現D5の選択証拠が必要。
D7$design-contracts入出力・責任分担・互換性など、分担間の約束を固定。
D8$decompose-tasks独立にレビュー可能なTaskへ分割。範囲と完了条件を定義。
D9$sequence-and-parallelize依存・書込み競合・資源競合を整理し、安全な並列順序を決める。
D10$prepare-worker-briefs各子ワーカーへ渡す最小限の入力・作業範囲・検証・停止条件を作る。
D11$plan-verification-and-recovery検証・レビュー・復旧・受渡しと有限の時間／回数予算を固定。
D12$implementation-readiness-reviewD1〜D11を横断して着手可能か確認。不足は担当する上流Skillへ戻す。
feature / bug-fix / improvementの23個のprofile stepは、選ばれたD/EのSkill内に組み込む検査・作業です。別途23個のSkillを呼ぶ意味ではありません。また、profileのF1と共通closureのF1は別物です。

B7 / C6 / D12の終了GroupのF1〜F7完了後に行う。受理済みbundle/checkpoint、次Groupの案内、承認・残予算。
Grilling等の質問中質問のたびには行わない。同じSkill内で回答を整理。不明点が残れば同じSkillを再開する。
保存失敗・blocked未保存のまま次へ進まない。停止理由と証拠を先に保存。clear自体は問題の解決や承認にならない。
Eの子ワーカー各attemptをfresh contextで起動。親がTask/Review packageを渡す。利用者が各子へ手動clearする運用ではない。
Eの親 / G / H保存されたEpoch境界・Group終了時の案内に従う。checkpointから再開。B/C/Dの「全Skillごと」を全Groupへ無条件に拡張しない。

ここでのclearは、ホストの会話を空にする操作、または過去の会話を継承しない新しい会話への移行です。履歴をコピーするforkや、同じ会話内の要約は同じ意味ではありません。補助スクリプトはホストのclearを操作・証明しません。

clearしてもファイル・目的承認・消費済み予算・Findingは残ります。回数や期限をリセットするための操作ではありません。

05 / EXECUTION & TWO-STAGE REVIEW

Eは「レビューの後に、指摘を評価する」

$execution-preflight
対象：/absolute/project
Run ID：実際のrun-id
保存済みD closure / handoff：/absolute/project/.../handoff.json
現HEAD、承認、D8のTask、D10のbrief、D12のready判定を検証してください。
通過した場合だけ、承認済み範囲と残予算でGroup Eを進めてください。
review候補は単一の独立Validatorで評価し、requiredだけを修正してください。
予算不足・権限外・重大な未解決は止め、理由と再開条件を残してください。

E1単体は検査であり、dispatchや外部操作の許可は出しません。後続を進めるには、実際の承認と有効なTask package・書込み範囲が必要です。

ID親が手配するSkill役割・分岐
E1$execution-preflight最新状態、依存、権限、競合、有限予算を確認。
E2$dispatch-taskreadyなTaskを変更不可の狭いpackageにする。
E3$execute-small-loop子Workerが作成・focused test・自己点検。自己点検は独立レビューの代わりではない。
E4$review-task-specfresh Reviewer：仕様・アーキテクチャ・安全性。同じ凍結candidateをE5と並列に見る。
E5$review-task-qualityfresh Reviewer：品質・統合・運用性・証拠。
E6$validate-review-findings別の単一Validatorが両レビューを結合し、required / defer / reject / needs-userを判定。
E7$fix-and-rereviewrequiredがあるときだけ修正とfresh再レビュー。E6へ戻る。
E8$converge-parallel-batch受理済みの並列成果を統合。意味判断が必要なら別の統合Worker＋レビューへ。
E9$verify-whole-change統合した全変更を、計画・元の目的への寄与に照らしてfresh検証。
E10$arbitrate-exception競合・予算切れ・仕様欠陥等で通常経路が止まった場合のみ、有限の仲裁案を出す。

典型的な分岐

E1 → E2 → E3 → E4とE5を並列 → E6

  • requiredあり：E7で修正・再レビュー → E6で再評価。
  • requiredなし：E8で収束 → E9で全体検証 → Groupの終了処理。
  • 人間判断・未解決・予算不足：停止。必要に応じE10へ。軽微な指摘を消すためだけに繰り返さない。

Validatorは、背景・As-Is・正本のTo-Be・差分・証拠を確認します。重複、理由のある既存選択、軽微な改善提案をそのまま修正指示へ変換しません。Workerは自分のFindingを閉じず、Reviewerは実装を変更せず、Validatorも修正しません。

macOS practical threat boundary

機密性が必要なbroker-only Taskの実用プロファイルは macos-parent-writer-practical/v1 です。正本は r5-practical-profile-approval/v1（approval digest sha256:2f0ae19fac7b90778d1b5713c51071f1ab7e96ce179237a1e5892cf320dfaefb）です。trusted側はCodex host、parent Orchestrator、same-UID parent runtime processで、親が唯一のstate writerです。adversarial側はsandboxed task child、malformed or stale caller input、その子に許された範囲で可能なpath substitutionです。

E2はTaskの全write rootとbroker state rootが、同一・包含・被包含のいずれにもならないことを確認します。sandboxはTask childによるbroker stateの読取り・変更を拒否します。E3はcallerの自己申告ではなく、parent_authenticated_receipt=true のv2 receiptを親経由で読み直し、非重複、descriptor anchoring、no-follow、device/inodeの再確認、publication前後のattachment check、defense-in-depthのrollbackを検証します。

このプロファイルが保証しないこと
receiptには次のaccepted residualをそのまま残します。
  • a malicious external process running as the same login UID may rename a project ancestor
  • SIGKILL of the trusted parent after a publication syscall and before bookkeeping may leave bytes in a detached tree
arbitrary_same_uid_atomicity=false、publication_sigkill_atomicity=false です。attachment checkやrollbackは防御を重ねるものですが、この2つをtrueにする保証ではありません。別OS principal、privileged service、launchd unit、non-writable mountは実装しておらず、activation済みとも扱いません。
06 / ARCHITECTURE

業務上の構造は Workflow → Group → Skill の3層です。これとは別に、実行時の「人・薄い親Controller・子の専門役割」と、状態を守る「DAG Orchestrator / Control Kernel」があります。Skillの数だけ常駐エージェントがいるわけではありません。

Skill = 手順と契約

必要入力、範囲、出力、完了・停止条件を定義。Skillだけでは無人の常駐実行基盤になりません。

Package = 子への依頼書

必要な背景と物理参照、受入条件、非目標、書込み範囲、予算を渡す。無関係な会話全文は渡しません。

Receipt = 確認の証拠

誰が、どの版の何を検証・承認したかを固定。短い報告でも、元のファイルへ追跡できます。

並列化の単位は、依存が満たされて競合しないTask。前提成果が未受理のTaskを先走らせたり、同じファイルを複数Workerへ同時に書かせたりしません。実行環境のcapacityの制約は残ります。役割の独立性は単に名前を変えることではなく、入力とcontext・担当を分離して維持します。

Context Epochは会話の区切りを記録する実行メタデータです。第4の業務階層ではありません。親も必要な境界でcheckpointから再開するため、1本の巨大な会話を永続させる設計ではありません。

コード以外にも、目的・成果・判断を扱える

B/C/D/G/Hは、コードを唯一の成果物とする手順ではありません。下表はsource上の経路と、それに合う目的の例です。すべてを本番で自動完走できるという一覧ではありません。

H2$decide-run-outcome人間が achieved / partially achieved / not achieved / superseded / abandoned を判定。
H3$archive-or-continue証拠・復旧手段の保持と、アーカイブまたは継続の引き継ぎを計画。

たとえば「FAQを改稿してテストした」はdelivery、「問い合わせが減った」はoutcomeです。効果の観測期間がまだ来ていなければ、未測定として残します。H2/H3の記録自体は、ファイル削除・新Run作成・本番操作を自動許可しません。

状態確認の例（変更しない操作）

/absolute/project/.agent-workflow/bin/agent-workflow-inception \
  resume --handoff /absolute/project/.../handoff-0001.json

/absolute/project/.agent-workflow/bin/agent-workflow-inception runtime status --project /absolute/project --run-id actual-run-id

前者は同一snapshotのwrapperでdraft/handoffを検証し、frontier_status: helper-verifiedが返った場合だけ次の状態として採用します。手書きJSONやagentの成功メッセージはfrontierではありません。後者は実Runの状態を確認するものです。返ってきたnext adviceは実行済みという意味ではありません。状態を見てから、適切なSkillを明示して再開します。

ファイルの役割と、実Run採用時の注意
  • .agent-workflow/SNAPSHOT-MANIFEST.json：review済みrelease manifestのdigestと、project-local Skill、runtime、schema、Workflow、Group、catalog、wrapperの同一snapshotを固定。wrapperは毎回全対象byte・mode・managed inventoryを検証する。
  • .local/agent/inception/…：pre-Runの依頼・出力・helper proof付きhandoff。新規受付の保存で勝手にRunを初期化しない。
  • .local/agent/runs/<run-id>/control-kernel/：実Runのtransaction、object、HEAD等。会話要約ではなく、検証されたこの状態を基準にする。
  • Artifactの参照はpath・version・digestで結合。ファイルを後から手編集した場合、古いreceiptはそのまま使えない。
  • 実行Taskのread scopeは宣言と観測receiptへ固定する。ただし通常receiptはOS全体のallow-listを意味せず、OS隔離を使わない限り os_isolation_enforced=false とする。
  • adoptには preapproval_steps としてB1〜B6の正確な6入力が必須。詳細な引数と承認receiptの形式はsingle-Skill protocolに従う。
  • realな人間承認と、明示許可されたrehearsalのmock承認は分離。テスト用driverの固定入力を通常案件の判断として流用しない。
  • project-local Runを操作しても、global current Run/objective pointerを変更する機能ではない。
10 / OPERATING NOTES

時間・承認・止まったときの扱い

時間を守るには、最初に「今回の上限」を置く

実行前にworkflow-loop/v1のphase policy、論理作業ID、検証範囲、回復経路を固定します。initial attemptは追加反復に数えず、技術的retryは別枠1回です。clear、再開、rename、candidate更新で同じ仕事のcounterはresetしません。process/tool timeoutは一回の呼出し監視として保持し、phase全体の残時間には変換しません。

予算不足でrequiredが残れば停止であり、完成ではありません。軽微な問題は根拠付きでdeferし、成功した成果物も保存します。ループ名やFinding IDを変えてやり直し回数を消す運用にしません。予算切れからの再開は、新しい明示承認と検証されたreopenが必要です。

過去のこの開発セッションで使った「Section-wide fast mode」「全体5時間」「修正wave数」等の一時的な指示を、全案件の製品defaultとみなさないでください。また、helperの期限チェックは次の操作を拒否するもので、動作中の外部AIプロセスを時刻どおり強制終了する監督ではありません。

承認を軽くできるところ・別扱いにするところ

内容扱い
進捗の表示・根拠の読取り毎回の承認待ちにする必要はない。開始・終了・停止理由・次の一手を短く表示する。
承認済みTask内の作成・テスト有効な権限・範囲・予算内で進める。進捗表示の許可を実行権限の代わりにしない。
目的承認・重要な選択・昇格・最終結果B7、D5→D6の選択、G5、H2等は、対象と結び付いた人間の判断が必要。
外部送信・credential・本番設定・公開別の保護された承認境界。Nix activation、Git commit/push等も今回の具体的な権限を確認する。

止まったら、この5点を返してもらう

現在地：Run / Group / Skill / revision
完了済み：受理された成果物と検証の参照
停止理由：不足入力・権限・予算・不整合等の具体的な原因
未実施：残るrequired、未検証、defer
次の一手：誰が何を用意・承認し、どのSkillから再開するか

「完了です」だけで判断せず、何が閉じたのかを確認します。draft保存、compiler通過、Task成功、E closed、目的達成、本番反映はそれぞれ別です。
