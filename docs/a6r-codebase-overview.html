01 / Executive model

要約

このシステムの中心は「一つの可変ポインタ」と「それ以外の不変な証拠」です。

01

正本はHEADから辿る

ObjectとTransactionはdigestで識別され、canonical stateはHEADが指すTransaction chainから復元します。表示用ファイルは正本ではありません。

02

書き込み主体を分離する

WorkerとReviewerはinboxへ提出するだけです。権限・scope・expected HEADを検証したOrchestratorだけがstate transitionをcommitします。

03

レビューは有限に収束する

候補抽出と必要性判定を別主体に分け、requiredだけを修正します。fingerprint重複、軽微事項、意図的選択を無限ループの燃料にしません。

完了の意味

A6Rはsource-onlyとisolated rehearsalの範囲で完了しています。実Runの移行、pointer cutover、A7、activation、Git操作は実施していません。

02 / Context map

誰が、何を決めるか

実装は能力を混ぜません。判断、提出、検証、状態遷移を物理的な境界で分けます。

Human authority

目的、重要な設計判断、reopen、移行/cutoverなどのmaterial decisionを承認する。承認はOperation・Run・budget・expected HEADへbindされる。

Orchestrator

command envelope、authority、assignment、scope、input digest、CASを検証し、唯一HEADを進める。Run stateのsingle writer。

Worker

Task Packageにbindされた入力とwrite scopeで作業し、結果またはstop reasonをinboxへ提出する。自分でstateをacceptしない。

Reviewer

fresh Epochとobject-bound Review Packageから候補Findingを作る。修正や「必要」の判定は行わない。

Finding Validator

Reviewerとは別のfresh assignmentで、全候補をrequired / defer / reject / needs-userへ分類する。

Fresh reader

会話履歴を使わず、HEAD・Transaction・Object・Bundle・Checkpointから現在地と次の一手を復元する。

03 / Atomic commit

一回の状態遷移

失敗はHEADの手前で止まり、成功だけが一つのatomic pointer swapとして見えます。

01Command

versioned envelope + idempotency key

02Validate

authority · scope · CAS · durable payload

03Stage

new Objects + Transaction in temp tree

04Publish

content-addressed immutable files + fsync

05 · COMMITAtomic HEAD

the only mutable canonical pointer

06Project

rebuild disposable human-facing views

HEADより前に落ちた場合

stagingをquarantineへ移し、publish済みTransactionはorphan evidenceとして記録します。recoveryはHEADを勝手に進めません。

HEADより後に落ちた場合

canonical commitは成立済みです。fresh readerがHEADから状態を検証し、欠損・不一致のprojectionを決定的に再構築します。

IdempotencyとCASは別の役割

同じkey・同じcommandは既存結果へ収束しますが、異なるcommandでのkey再利用は拒否されます。expected HEADは、最初のpublicationが古い状態へ適用されるのを防ぎます。

05 / Review convergence

候補抽出と必要性判定を分ける

Reviewerが見つけたものを即修正対象にせず、別Validatorが必要性を判定してからrequired-onlyの権限を発行します。

1. Candidate reviewStandards / Specを別軸で確認
2. Candidate set修正せずFinding候補だけを固定
3. Fresh Validatorrequired / defer / reject / needs-user
4. Required-only fixadmitted FindingだけをTDDで修正
5. Resolution claimWorkerは閉鎖できず証拠を提出
6. Fresh rereview別assignmentが解消と新規候補を確認
7. Close / terminal解消、または有限停止を正本化

ループ防止

同じfingerprintはFinding IDが違ってもduplicate dispositionとなり、新規Findingやreview round消費を起こしません。軽微・意図的選択はdefer/rejectに留められます。

reopenの条件

genericな承認IDだけでは再開できません。承認はreopen operation、対象Run、置換budget、現在HEAD、assignmentへ正確にbindされます。

06 / Migration & recovery

旧stateを壊さずに切り替える

変換とcutoverを分離し、読み比べ可能な候補を先に作ります。切替はpointerだけ、rollbackも物理的に有効な旧targetへだけ行えます。

READ-ONLYLegacyReader

raw bytes + source digest

ISOLATEDLegacyConverter

sanitize durable fields + attest

COMPAREOld / New Reader

same meaning, different storage

REBUILDProjection

recover from canonical HEAD

CASPointerCutover

approval + expected pointer

RECOVERYRollback

validate and restore old target

Source binding

入力ファイルのraw digest、logical source identity、変換attestationを保持し、別revisionの取り違えを拒否します。

Path safety

pointer pathはcanonical absolute pathだけを許可し、traversal、二重separator、symlink等のredirectを検証します。

Rollback truth

保存された文字列だけでなく、旧targetのHEADとRun identityが物理的に正しい場合にだけrollbackします。

ここで確認したのはisolated copyのrehearsalです。

実際のBootstrap Runは変換・cutoverしていません。pointerも変更されておらず、旧stateはそのままです。
